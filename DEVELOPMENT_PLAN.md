# План розробки продукту для пасажирських перевезень

Цей документ описує наступний етап проекту Logistic. Його можна передати іншому
розробнику або Codex як контекст для продовження розробки.

## Контекст бізнесу

Компанія має невеликий парк з 8 бусів Mercedes Sprinter для перевезення
пасажирів та багажу. Потрібен внутрішній продукт для адміністраторів і водіїв,
який показує поточну заповненість бусів, місце перебування транспорту та дані
пасажирів.

Основний сценарій: водій логіниться з планшета або лептопа, бачить поточну
картину по бусах, відкриває конкретний бус і працює з місцями та пасажирами.
Адмін має ті самі можливості, а також керує користувачами, бусами, маршрутами й
бачить аудит змін.

## Поточний стан проекту

Вже є базовий fullstack-фундамент:

- Backend: NestJS, PostgreSQL, JWT auth.
- Frontend: React, Vite, shadcn/ui-подібні компоненти.
- Є реєстрація, логін, ролі `admin` та `driver`.
- Є таблиця користувачів і адмін-дії над користувачами.
- Є простий механізм міграцій БД у `backend/src/database/migrations.ts`.

Роль `driver` є базовою неадмінською роллю. Нові зареєстровані користувачі
створюються як водії.

## Ціль MVP

MVP має дозволити:

1. Адміну створювати та редагувати буси.
2. Адміну або водію бачити список бусів із заповненістю місць.
3. Адміну або водію відкривати сторінку конкретного буса.
4. На сторінці буса бачити схему місць: вільні та зайняті місця різними
   кольорами.
5. По кожному зайнятому місцю бачити дані пасажира:
   - ім'я;
   - прізвище;
   - телефон;
   - місце посадки;
   - місце висадки;
   - кількість багажу;
   - коментар, якщо потрібен.
6. Водій або адмін може змінювати інформацію по місцю/пасажиру.
7. Для кожної зміни зберігається, хто її зробив і коли.
8. Адмін бачить останнього редактора та історію змін.

## Ролі та доступи

Ролі:

- `admin`: повний доступ.
- `driver`: доступ до перегляду бусів, місць, пасажирів і редагування робочої
  інформації.

Права:

- `admin`:
  - керування користувачами;
  - призначення ролей;
  - створення/редагування/деактивація бусів;
  - перегляд і редагування всіх місць і пасажирів;
  - перегляд аудиту змін.
- `driver`:
  - перегляд списку бусів;
  - перегляд сторінки буса;
  - створення, редагування й очищення бронювання місця;
  - перегляд інформації про останню зміну.

## Модель даних

Рекомендовані таблиці:

### `vehicles`

Буси компанії.

Поля:

- `id`
- `name`: наприклад `Sprinter 1`
- `plate_number`: номер авто
- `seat_count`: кількість пасажирських місць
- `status`: `active`, `inactive`, `maintenance`
- `current_location`: текстове поле для поточного місця перебування
- `created_at`
- `updated_at`

### `vehicle_seats`

Фізичні місця в бусі.

Поля:

- `id`
- `vehicle_id`
- `seat_number`: номер місця
- `position_row`: ряд для візуальної схеми
- `position_col`: колонка для візуальної схеми
- `is_active`

Для MVP місця можна створювати автоматично від `1` до `seat_count`. Якщо схема
Sprinter має бути точною, тоді треба явно зберігати `position_row` і
`position_col`.

### `passenger_bookings`

Поточна зайнятість місць.

Поля:

- `id`
- `vehicle_id`
- `seat_id`
- `first_name`
- `last_name`
- `phone`
- `pickup_location`
- `dropoff_location`
- `baggage_count`
- `comment`
- `status`: `active`, `cancelled`, `completed`
- `last_modified_by_user_id`
- `created_at`
- `updated_at`

На MVP можна вважати, що на одне активне місце є максимум один активний запис у
`passenger_bookings`.

### `change_logs`

Аудит важливих змін.

Поля:

- `id`
- `entity_type`: наприклад `vehicle`, `seat`, `passenger_booking`
- `entity_id`
- `action`: `create`, `update`, `delete`, `clear_seat`
- `changed_by_user_id`
- `before_data`: JSONB
- `after_data`: JSONB
- `created_at`

Для MVP достатньо логувати зміни `passenger_bookings`.

## Backend API

Рекомендовані endpoint-и:

### Vehicles

- `GET /api/vehicles`
  - список бусів із заповненістю;
  - доступ: `admin`, `driver`.
- `POST /api/vehicles`
  - створити бус;
  - доступ: `admin`.
- `GET /api/vehicles/:id`
  - деталі буса, місця, активні пасажири;
  - доступ: `admin`, `driver`.
- `PATCH /api/vehicles/:id`
  - оновити дані буса або поточну локацію;
  - доступ: `admin`, частково `driver` для `current_location`.

### Seats and passenger bookings

- `PUT /api/vehicles/:vehicleId/seats/:seatId/booking`
  - створити або оновити пасажира на місці;
  - доступ: `admin`, `driver`.
- `DELETE /api/vehicles/:vehicleId/seats/:seatId/booking`
  - очистити місце;
  - доступ: `admin`, `driver`.

### Audit

- `GET /api/audit`
  - список змін;
  - доступ: `admin`.
- `GET /api/vehicles/:id/audit`
  - історія змін по конкретному бусу;
  - доступ: `admin`.

## Frontend екрани

### Dashboard

Поточний dashboard треба перетворити з таблиці користувачів на операційний
екран:

- верхня панель з користувачем, роллю, logout і theme toggle;
- список/сітка бусів;
- для кожного буса:
  - назва;
  - номер авто;
  - поточна локація;
  - кількість зайнятих місць;
  - кількість вільних місць;
  - візуальна міні-схема місць.

Кольори місць:

- вільне: нейтральний/сірий або зелений;
- зайняте: синій або жовтий;
- проблемне/потребує уваги: червоний, якщо буде окремий статус.

### Vehicle Detail Page

Сторінка конкретного буса:

- заголовок із назвою буса, номером авто, локацією;
- схема місць;
- список або панель деталей для вибраного місця;
- форма пасажира:
  - ім'я;
  - прізвище;
  - телефон;
  - місце посадки;
  - місце висадки;
  - кількість багажу;
  - коментар;
  - кнопки зберегти/очистити місце.
- блок "Остання зміна":
  - хто змінив;
  - коли змінив.

### Admin Screens

Після MVP:

- користувачі та ролі;
- керування бусами;
- журнал змін;
- налаштування схем місць.

## Етапи реалізації

### Етап 1. Ролі та міграції

- Роль `driver` вже додана у backend і frontend constants.
- Є frontend `RoleRoute` для рольового роутингу.
- Додати міграції для `vehicles`, `vehicle_seats`, `passenger_bookings`,
  `change_logs`.
- Додати seed або migration для 8 бусів.

Критерій готовності: backend стартує, БД має нові таблиці, старі auth/users
функції працюють.

### Етап 2. Backend домен бусів

- Додати `vehicles` controller/service.
- Додати endpoint `GET /api/vehicles`.
- Додати endpoint `GET /api/vehicles/:id`.
- Порахувати заповненість місць на backend.
- Додати створення/оновлення booking для місця.
- Додати аудит змін booking.

Критерій готовності: через API можна отримати буси, місця, пасажирів і змінити
пасажира на місці.

### Етап 3. Frontend dashboard

- Додати API-клієнт `frontend/src/api/vehicles.js`.
- Замінити основний dashboard для driver/admin на список бусів.
- Додати компонент картки буса з міні-схемою місць.
- Додати route `/vehicles/:id`.

Критерій готовності: водій після логіну бачить 8 бусів і їхню заповненість.

### Етап 4. Сторінка буса

- Додати сторінку деталей буса.
- Додати клікабельну схему місць.
- Додати форму редагування пасажира.
- Показувати останнього редактора.
- Після збереження оновлювати стан сторінки.

Критерій готовності: водій може відкрити бус, натиснути місце, змінити
пасажира, і це видно іншим користувачам після оновлення.

### Етап 5. Адмін-функції

- Винести таблицю користувачів в admin section.
- Додати керування бусами.
- Додати перегляд audit log.
- Додати фільтри за бусом, датою, користувачем.

Критерій готовності: адмін може керувати системою без прямого доступу до БД.

### Етап 6. Production readiness

- Додати `.env.example`.
- Додати `docker-compose.prod.yml`.
- Закрити Postgres порт назовні у production.
- Налаштувати backup БД.
- Обмежити CORS production-доменом.
- Додати базові тести backend-сервісів.

## UX вимоги

- Інтерфейс має бути зручним на планшеті та лептопі.
- Кнопки й місця мають бути достатньо великими для touch.
- Основний екран має швидко відповідати на питання:
  - який бус де знаходиться;
  - скільки місць зайнято;
  - які місця вільні;
  - хто їде і куди.
- Не робити маркетингову landing page. Перший екран після логіну має бути
  робочим dashboard.

## Технічні правила для наступного розробника

- Не додавати shipping/shipments домен. Для цього продукту використовувати
  терміни `vehicles`, `seats`, `passenger_bookings`.
- Всі зміни БД робити через `backend/src/database/migrations.ts`.
- Не змінювати дані напряму в БД, якщо це можна оформити міграцією.
- Після змін запускати:
  - `cd backend && npm run build`
  - `cd frontend && npm run build`
- Якщо змінюється backend у Docker, перебілдити:
  - `docker compose up --build -d backend`
- Після міграцій перевіряти:
  - `GET /api/health`
  - список таблиць у Postgres.

## Відкриті питання

- Скільки місць у кожному Sprinter і чи однакова схема салону для всіх 8 бусів?
- Чи потрібні маршрути/рейси з датами, чи MVP показує тільки поточний стан бусів?
- Чи має водій бачити всі буси, чи тільки призначені йому?
- Чи потрібна історія пасажирів після завершення поїздки?
- Чи потрібна підтримка кількох рейсів на день для одного буса?
- Чи потрібен offline mode на планшеті, якщо немає інтернету?
